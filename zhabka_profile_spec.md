# Zhabka — спецификация профиля пользователя и правки UI

Это техническое задание на доработку. Не переизобретай архитектуру —
следуй схеме ниже, она уже согласована.

---

## 1. Единый источник правды: profile.json

Все данные о пользователе (и то, что он написал в чат, и то, что выставил
руками в Profile) живут в ОДНОМ объекте. Нет отдельного "состояния чата"
и отдельного "состояния формы" — есть один профиль, который читают и
пишут разные экраны.

```json
{
  "role": "Product Designer",
  "experience": "1-3 years",
  "workFormat": {
    "remote": true,
    "hybrid": false,
    "office": false,
    "relocate": false
  },
  "officeLocations": [],
  "hideB2B": true,
  "minSalary": null,
  "resume": {
    "filename": null,
    "uploadedAt": null
  },
  "aiNotes": [
    "Не хочет работать в аутсорсе",
    "Открыт к релокации в Польшу"
  ]
}
```

Поля `role`, `experience`, `workFormat`, `officeLocations`, `hideB2B`,
`minSalary`, `resume` — структурированные, их можно менять и через чат
(AI распознаёт и обновляет), и вручную на экране Profile.

`aiNotes` — единственное поле, куда пишет **только AI**, по мере диалога.
Это не текстовое поле для ручного ввода. Пользователь не может печатать
в него напрямую — только видит как read-only список на экране Profile.
Если хочет что-то поменять — идёт в чат.

**Убрать полностью:** поле "About you" (textarea) с экрана Profile.
Оно дублирует чат тем же способом ввода без ясности, кто его читает.
Заменяется на read-only список `aiNotes` (см. выше).

**Убрать:** поле Language с экрана Profile — это свойство конкретной
вакансии, а не глобальная настройка человека.

**Добавить:** `relocate` как ещё один чекбокс рядом с remote/hybrid/office
в блоке Work format.

## 2. Правило записи (кто и когда меняет profile.json)

- **Чат** читает текущий `profile.json` перед каждым запросом к AI, передаёт
  его в промпт вместе с сообщением пользователя. AI возвращает обновлённый
  объект целиком (или diff). Приложение сохраняет его как новый `profile.json`.
  После сохранения AI отвечает в чате коротким текстовым эхо того, что
  реально изменилось — это просто человекочитаемое подтверждение записи,
  не отдельное состояние.

- **Экран Profile** — обычная форма с двусторонним биндингом к тем же
  полям `profile.json`. Никакого AI здесь не участвует — прямое изменение
  значения по клику/вводу, как в любой форме настроек.

- **Последнее действие побеждает.** Написал в чате в 14:00 — обновилось
  поле. Поправил вручную в Profile в 15:00 — снова обновилось. Конфликта
  "что если в двух местах разное" не возникает, потому что это один объект,
  а не два независимых.

- **Резюме** — один и тот же upload-хэндлер вызывается и из кнопки-скрепки
  в чате, и из блока Resume на экране Profile. Оба пишут в
  `profile.resume`. Экран Profile просто отображает текущее состояние
  этого поля и даёт кнопку "заменить".

## 3. Разделение Profile vs Settings (оставить как есть, только формулировка)

- **Profile** = "кого я ищу и на что готов" — всё, что участвует в
  сравнении вакансии с пользователем (role, experience, workFormat,
  officeLocations, hideB2B, minSalary, resume, aiNotes).

- **Settings** = "как работает приложение" — API-ключ провайдера, список
  источников (включен/выключен, добавить новый). Никогда не влияет на
  то, что AI решает про вакансию — только на то, откуда берутся данные.

## 4. Доработка экрана Settings

Сейчас список источников — это просто текст без возможности управления.
Нужно:

1. **Toggle-переключатель** (не чекбокс) у каждого источника — визуально
   как iOS-свитч: капсула шириной ~36px, высотой ~20px, кружок внутри
   сдвигается влево/вправо, background капсулы `var(--bg-hover)` в
   выключенном состоянии → `var(--accent)` во включенном, кружок белый.
   Выключенный источник не блокируется полностью в списке — просто
   тусклее (`opacity: 0.5` на всём `.source-item`), чтобы было видно,
   что он есть, но временно не участвует.

2. **Поле "Добавить источник"** над списком — текстовый инпут с
   плейсхолдером "@username или ссылка на папку Telegram" и кнопкой
   "Добавить" справа (тот же стиль, что `.chat-send`, но прямоугольная
   маленькая, не круглая). При отправке ссылки на папку — использовать
   уже готовую логику извлечения каналов из папки (см. наши прошлые
   скрипты), при отправке одиночного username — добавить один источник.

3. **Больше воздуха между блоками** — увеличить `margin-bottom` у
   `.section` с 32px до 40-48px, добавить `padding: 20px` вокруг
   каждого смыслового блока (AI-провайдер, источники) с лёгким
   `background: var(--bg-elevated)` и `border-radius: var(--radius-lg)`,
   чтобы блоки визуально разделялись как карточки, а не сливались в
   одну простыню полей.

## 5. Общие визуальные правки (продолжение системы токенов, ничего нового не вводить)

- Все инпуты/селекты/textarea — единая высота `44px` (сейчас есть
  расхождения между `.custom-select`, `.custom-input`, `.chat-input`).
- Между `.section-head` (лейблом блока) и содержимым — всегда `12px`,
  сейчас местами `8px`, местами `10px` — привести к одному значению.

  соседствовать в одном блоке как равнозначные — переключатели (Settings)
  и пилюли-мультивыбор (Profile: work format) — разная механика для
  разных задач, это нормально, просто не путать одно с другим в одном
  ряду.
- Убедиться, что во всех местах (Profile, Settings, RightDrawer)
  используются переменные из `theme.css`, никаких новых hex-цветов.

## 6. Дополнение: автозаполнение, чат-бабблы, мелкие правки

### 6.1 Автозаполнение Profile из чата и резюме

Когда AI извлекает из сообщения в чате или из текста резюме значение,
которое соответствует СТРУКТУРИРОВАННОМУ полю профиля (role, experience,
workFormat, minSalary и т.д.) — оно пишется прямо в это поле, а не только
в `aiNotes`. Пользователь сказал в чате "ищу продуктового дизайнера,
опыта коммерческого нет" → `profile.role = "Product Designer"`,
`profile.experience = "No commercial experience"` записываются напрямую.

`aiNotes` используется только для того, что НЕ имеет структурированного
поля (например "не хочет аутсорс", "открыт к релокации в Польшу").

Следствие: экран Profile никогда не должен выглядеть пустым для
пользователя, который уже пообщался в чате или загрузил резюме — все
распознанные структурированные поля должны быть видны заполненными,
когда он туда заходит. Ручной ввод в Profile и есть то же самое поле,
которое мог бы заполнить AI — они неразличимы по итоговому значению.

Добавить на экран Profile ненавязчивую подсказку прогресса заполнения,
например: `Profile completeness: 3 of 7 fields — more detail improves matching`.
Не блокирующая, не в виде прогресс-бара с давлением, просто маленькая
строка серым текстом.

### 6.2 Role — заменить select на текстовое поле с пилюлями-подсказками

Убрать `<select>` для Role. Заменить на обычный текстовый `<input>`
с плейсхолдером `e.g. Product Designer`, и рядом строка кликабельных
пилюль с частыми вариантами (`Product Designer`, `UX/UI Designer`,
`Product + UX/UI`) — клик по пилюле просто вписывает текст в поле,
это не альтернативный источник данных, а быстрый способ его заполнить.
Причина: значение в это поле может прийти и из чата в произвольной
формулировке ("Junior Product Designer, фокус на AI-продукты") — жёсткий
список вариантов такое не вместит, а текстовое поле — вмещает всегда.

### 6.3 Salary — валюта и toggle "скрывать без зарплаты"

- Рядом с полем ввода минимальной зарплаты добавить маленький селектор
  валюты (`₽ / $ / €`), по умолчанию `₽`. Без него число в поле
  неоднозначно.
- Под полем добавить toggle (тот же компонент свитча, что и в Settings
  для источников) — `Hide vacancies without listed salary`, по умолчанию
  выключен.

### 6.4 Employment / Hide B2B — убрать как отдельный структурированный toggle

Убрать блок Employment с чекбоксом "Hide B2B vacancies" с экрана Profile
целиком — это недостаточно важный и недостаточно чёткий критерий для
отдельного элемента управления. Если пользователь хочет исключить B2B —
это делается через чат ("не показывай B2B/аутсорс") и попадает в
`aiNotes`, а не в отдельное структурированное поле профиля.

### 6.5 Sidebar — статус синхронизации источников

В нижней части сайдбара (сейчас там просто текст "zhbka · personal ai
job inbox") добавить строку со статусом:

```
37 sources · Last sync 18:00
```

Данные берутся из Settings (число включённых источников) и из времени
последнего успешного прогона сборщика вакансий.

### 6.6 Кнопка ручной синхронизации в чате

Пока сбор вакансий не автоматизирован по расписанию, нужна кнопка/команда
в интерфейсе чата — что-то в духе "Sync now" рядом с полем ввода или
как быстрая команда — которая запускает прогон по источникам вне
расписания и присылает в чат новый улов, если что-то нашлось. Это
временное решение для ручного режима, до подключения крона/фоновой
задачи.

### 6.7 Кнопка прикрепления резюме в чате

В `ChatInput` рядом с текстовым полем добавить кнопку (иконка `+` или
`Paperclip` из lucide-react) с явным лейблом/tooltip `Add CV (PDF)` —
не универсальная кнопка "прикрепить файл", а конкретно про резюме,
чтобы не создавать ложных ожиданий про картинки/другие форматы.
`accept=".pdf"` на input[type=file]. Загруженный файл пишет в то же
поле `profile.resume`, что и загрузка на экране Profile (см. раздел 2).

### 6.8 Чат — визуальная иерархия трёх типов контента

Сейчас все сообщения в чате выглядят одинаково. Нужно три разных
представления:

1. **Сообщение пользователя** — баббл, выровнен вправо, заливка
   `var(--accent-soft)`, текст `var(--text-primary)`.
2. **Текстовый ответ AI** (короткие реплики вида "Понял, исключаю B2B")
   — выровнен влево, БЕЗ фона-пузыря, просто `var(--text-secondary)`,
   маленькая иконка "глаза жабки" слева вместо аватарки.
3. **Карточка вакансии в чате** — это тот же компонент `JobCard`, что и
   в Inbox, отрендеренный на всю доступную ширину БЕЗ баббл-обёртки —
   вакансия не является репликой диалога, это контент, который жабка
   "положила на стол", визуально это должно читаться иначе, чем
   переписка.

### 6.9 Пустые состояния (empty states)

Добавить понятные плейсхолдеры вместо пустых экранов:
- Inbox без вакансий: `No vacancies yet. Zhabka is watching your sources.`
- Bookmarks пуст: `Nothing saved yet.`
- Settings → Sources, если поиск не дал результатов: `No sources match your search.`
Не просто пустой блок — короткая фраза по центру, `var(--text-muted)`.

### 6.10 Язык интерфейса — английский

Все статичные строки интерфейса (лейблы, кнопки, плейсхолдеры, пункты
меню) — на английском, независимо от языка пользователя. AI в чате
отвечает на языке, на котором пишет пользователь. Вакансии показываются
как есть, на языке оригинального поста — не переводятся.

### 6.11 Скроллбар — у края окна, а не у края layout-блока

Сейчас скролл, судя по всему, навешен на внутренний контейнер с
паддингами, из-за чего скроллбар отображается не у самого края окна
браузера, а с отступом внутри layout. Правильная структура: `overflow-y:
auto` должен быть на внешнем контейнере, который занимает всю высоту
вьюпорта (`height: 100vh`) и тянется до самого края окна, а внутренние
отступы (padding) — на дочернем `-inner`-контейнере внутри него, а не на
самом скроллящемся элементе. Проверить `.main` / `.main-inner` (или
аналогичные) на этот паттерн и поправить, если паддинг сейчас висит на
элементе с `overflow-y`.

## 7. Дополнение: структура aiNotes и иерархия полей JobCard

### 7.1 aiNotes — типизированные заметки, не свободный текст

`aiNotes` — это не список произвольных предложений, а список маленьких
типизированных объектов:

```json
"aiNotes": [
  { "type": "exclude", "text": "Gamedev" },
  { "type": "exclude", "text": "B2B" },
  { "type": "condition", "text": "Office/hybrid only in Saint Petersburg" },
  { "type": "include", "text": "Open to AI-related products" }
]
```

`type` — один из `exclude` / `condition` / `include`. Рендерится теми же
компонентами `.ai-dot` / цветами, что уже используются в вердикте
`JobCard` (`exclude` → `var(--bad)`, `include` → `var(--good)`,
`condition` → `var(--warn)`). Один и тот же визуальный язык (красная/
зелёная/жёлтая точка) должен использоваться и в Profile, и в каждой
карточке вакансии — пользователь учит его один раз.

**Как AI поддерживает список без дублей:** при каждом сообщении в чате в
промпт передаётся текущий `aiNotes` целиком вместе с новым сообщением
пользователя, с инструкцией обновить список как редактируемое
состояние, а не как лог:
- если новое сообщение уточняет/переформулирует существующую заметку —
  заменить её текст, не добавлять вторую;
- если явно противоречит существующей — заменить;
- если это новая, не пересекающаяся тема — добавить.

AI возвращает обновлённый массив `aiNotes` целиком, который полностью
заменяет предыдущий (не патч, не аппенд на стороне фронтенда).

### 7.2 JobCard — новая иерархия полей

Порядок и вес элементов на карточке должен буквально повторять порядок,
в котором человек, долго ищущий работу, проверяет вакансию — сначала
"не пошлют ли меня сразу", и только потом "какие условия".

Сверху вниз, по убыванию визуального веса:

1. **Title** — крупно, `var(--font-display)`, первое, на что падает
   взгляд. Без изменений от текущей реализации.

2. **Experience** — выносится в отдельную строку сразу под title, НЕ
   как один из тегов в общей строке с зарплатой/форматом. Формат:
   `3+ years · not strict` или `3+ years · required` — вторая часть
   явно показывает степень строгости требования, это и есть тот самый
   разбор "3 года будут преимуществом" vs "обязательны", ради которого
   весь проект затевался.

3. **Requirements** — компактный список конкретных технических
   требований (не абзац текста, не общие фразы). AI должен извлекать
   их как есть из текста вакансии, включая случаи явного
   несоответствия title, например если в требованиях есть Illustrator/
   After Effects/подготовка презентаций при тайтле "UX/UI Designer" —
   это должно остаться видимым в списке, не сглаживаться до общего
   "design skills".

4. **Причины показа (reasons)** — короткий чек-лист ✓/⚠/✕, БЕЗ
   категориального лейбла сверху вроде "Good match"/"Worth applying" —
   такие лейблы абстрактны и не отвечают на реальный вопрос пользователя
   ("почему я вообще это вижу"). Список причин уже сам по себе и есть
   ответ, ничего дополнительно резюмировать не нужно. Например:
   ```
   ✓ Product Design
   ✓ Remote
   ⚠ 3+ years required
   ```
   Если данных в посте было мало — одна из причин прямо это называет
   ("Not enough details — open original to check"), а не изобретает
   уверенность на пустом месте.

5. **Company / salary / work format / location** — второстепенный слой,
   приглушённая строка тегов рядом с мета-данными канала/времени внизу
   карточки, тем же визуальным весом, что сейчас у `.card-tags`. Это
   информация "если вакансия прошла первый фильтр, на каких условиях" —
   не то, на что падает взгляд в первую секунду.

**Воздух:** между блоками (title → experience → requirements → verdict)
добавить чуть больше вертикального отступа и, где уместно, тонкий
разделитель `border-top: 1px solid var(--border)` — сейчас разделитель
есть только перед AI-секцией, стоит применить тот же приём между
requirements и остальным содержимым, чтобы карточка читалась как
последовательность отдельных смысловых блоков, а не сплошной текст.

**Правая панель остаётся источником истины** — полный оригинальный
текст вакансии без сокращений и интерпретации живёт только в
`RightDrawer`, карточка в ленте — всегда сжатая выжимка по фиксированному
шаблону выше, никогда не показывает вакансию "как есть".

## 8. Дополнение: резолвер полного текста вакансии по ссылке

Многие посты в каналах — это краткая выжимка со ссылкой на другую
платформу (hh.ru, HireHi, карьерные страницы компаний). Чтобы AI
классифицировал вакансию точнее, перед отправкой в классификацию нужно
попробовать дотянуть полный текст по ссылке — отдельным шагом
("резолвером"), а не встраивая эту логику в сам промпт классификации.

### 8.1 Два уровня обогащения

1. **Известные платформы с настоящим API.** Пока единственная —
   hh.ru: открытый публичный API без авторизации
   (`api.hh.ru/vacancies/{id}`), нужен только заголовок `User-Agent`.
   ID вакансии вытаскивается из URL регуляркой. Ответ — структурированный
   JSON с полным описанием, зарплатой, ключевыми навыками. Не долбить
   API слишком часто — при коде ответа 403 останавливаться и не
   повторять запрос сразу.

2. **Универсальный fallback для всего остального** (HireHi, карьерные
   страницы компаний, любые будущие источники). Не пишем отдельный
   парсер под каждую платформу — просто забираем страницу как обычный
   публичный веб-запрос, вычищаем HTML (убираем `script`, `style`,
   `nav`, `footer`, `header`), получаем плоский текст. Работает для
   любой страницы, которая не требует логина — таких большинство у
   job-платформ.

Если ни один из способов не сработал (нет ссылки, страница за логином,
заблокировала запрос, слишком короткий ответ — вероятный признак
блокировки) — используем исходный текст поста из Telegram как есть.
Это не деградация, а честный fallback: AI работает с тем, что реально
есть, вместо того чтобы делать вид, будто данных больше.

### 8.2 Прозрачность источника обогащения

Рядом с каждой вакансией в данных сохраняется поле, откуда взят
итоговый текст для классификации: `hh.ru API` / `generic fetch` /
`telegram only`. Это не показывается как отдельный элемент интерфейса
пользователю, но полезно для отладки классификации и может в будущем
влиять на то, насколько уверенно AI формулирует вердикт (меньше
исходных данных — более осторожные формулировки, честные "not enough
info", а не выдуманная уверенность).

### 8.3 Куда встраивается в пайплайне

Резолвер — шаг между "получили пост из Telegram" и "отправили на
классификацию в LLM", применяется один раз к каждому посту перед первой
классификацией (не при каждом повторном открытии вакансии пользователем).
Пример реализации — см. `resolver.py`.

## 9. Дополнение: Inbox показывает только то, что стоит внимания

Изначальная идея продукта — "секретарь кладёт на стол только то, что
стоит внимания", не десятки вакансий подряд с пометкой "не подходит".

**Пересмотрено:** отдельная вкладка "Not for me"/архив отказов — не
нужна. AI теперь сам решает на этапе классификации, показывать вакансию
или нет (`aiVerdict.show: boolean`), и то, что решено не показывать, не
попадает в `vacancies_classified.json` вообще — ни в Inbox, ни в архив.
Специально хранить отказы бессмысленно: пайплайн работает на скользящем
окне последних 72 часов, старые непоказанные посты и так исчезнут из
выборки при следующем сборе, архивировать их незачем.

Итог: Inbox = все вакансии из `vacancies_classified.json` как есть,
без дополнительной фильтрации на фронтенде — фильтрация уже произошла
на бэкенде, до сохранения файла. Сайдбар остаётся как есть (Inbox,
Bookmarks, Profile, Settings) — без дополнительной вкладки.

### 11.1 Данные уже накапливаются по дням

`vacancies_classified.json` растёт со временем — каждый запуск
`classify.py` добавляет новые вакансии, не удаляя старые. У каждой

seenIds и для бэкапа/закладок (Bookmarks) — не полагайся на позицию в
массиве.

## 12. Дополнение: визуальный редизайн — мягкий, современный стиль

Цель — избавиться от ощущения "очевидно generic AI-интерфейса": меньше
жёстких границ, больше воздуха и мягких переходов, плавающие элементы
со стеклянным эффектом вместо сплошных панелей. Карточки вакансий
(JobCard) пока не трогаем — тестируем данные, редизайн карточек будет
отдельным шагом.

### 12.1 Новые токены (добавить в theme.css, не изобретать новые hex на лету)

```css
--glass-bg: rgba(18, 22, 29, 0.65);   /* полупрозрачная заливка под blur */
--glass-border: rgba(255, 255, 255, 0.06);
--shadow-soft: 0 4px 24px rgba(0, 0, 0, 0.28);
--shadow-soft-sm: 0 2px 12px rgba(0, 0, 0, 0.2);
--radius-lg: 18px;  /* было 16px — чуть мягче */
```

### 12.2 Системное правило: меньше границ, больше мягкой тени

Там, где сейчас `border: 1px solid var(--border)` используется просто
для отделения элемента от фона (карточки в Settings/Profile, chat
input, floating-кнопки) — замени на `box-shadow: var(--shadow-soft-sm)`
без бордера, оставляя `var(--border)` только там, где действительно
нужна чёткая структурная линия (например, разделители внутри списков).
Это не механическая замена всех бордеров без разбора — если элемент и
так на 100% непрозрачном фоне с явным контрастом (например, инпуты в
Settings) — можно оставить тонкий `border` пониженной непрозрачности
вместо тени, тень важна именно для *плавающих над контентом* элементов.

### 12.3 Inbox — плавающий хэдер вместо sticky-полосы

Убрать полноширинный sticky-инпут поиска. Вместо него — две круглые
кнопки (44px), закреплённые в правом верхнем углу поверх ленты (не
across всей ширины):

```css
.floating-header {
  position: sticky;
  top: 20px;
  z-index: 10;
  display: flex;
  justify-content: flex-end;
  gap: 8px;
  margin-bottom: -60px; /* не занимает место в потоке, парит над лентой */
  pointer-events: none; /* сама обёртка не блокирует клики по карточкам под ней */
}
.floating-btn {
  pointer-events: auto;
  width: 44px;
  height: 44px;
  border-radius: 50%;
  background: var(--glass-bg);
  backdrop-filter: blur(16px);
  -webkit-backdrop-filter: blur(16px);
  border: 1px solid var(--glass-border);
  box-shadow: var(--shadow-soft-sm);
  display: flex;
  align-items: center;
  justify-content: center;

  transition: width 0.25s ease, background 0.15s;
}
.floating-btn:hover { color: var(--text-primary); }
```

- **Кнопка поиска**: по клику `width` анимированно растёт (например,

- **Кнопка календаря**: по клику открывает popover под собой со списком
  дат (из уникальных `date` вакансий, сгруппированных по дню, см.
  раздел 11.2) — выбор даты скроллит/фильтрует ленту к нужному дню.
- Обе кнопки должны сдвигаться вместе с основным layout при открытии

  `position: fixed` относительно всего экрана) — сейчас RightDrawer уже
  реализован как flex-сосед основного контента на десктопе, а не оверлей

### 14.2 Баг: чипы Work format/City не переключаются (двойной клик)

Причина — известная особенность `<label>`, оборачивающего `<input>`, с
`onClick` на самом label: клик по label пересылается на input (нативное
поведение браузера), а затем всплывает обратно на label — один клик
пользователя вызывает `onClick` дважды подряд, переключение отменяет
само себя визуально. Раз чекбокс всё равно скрыт (`display: none
!important`) — он не нужен как реальный form-элемent, замени на кнопку
с ARIA-атрибутами вместо label+input, у кнопок нет этого поведения:

```jsx
{workFormatKeys.map((key) => {
  const checked = profile.workFormat[key]
  const label = key.charAt(0).toUpperCase() + key.slice(1)
  return (
    <button
      type="button"
      key={key}
      className={`checkbox-label ${checked ? 'checked' : ''}`}
      role="checkbox"
      aria-checked={checked}
      onClick={() => toggleWF(key)}
    >
      {label}
    </button>
  )
})}
```

Применить точно так же к чипам `officeLocations` (та же конструкция,
тот же баг). `.checkbox-label` в CSS уже полностью стилизован сам по
себе — на кнопке достаточно сбросить браузерные дефолты, если понадобится
(`border: none` уже задан классом, `font: inherit` можно добавить при
необходимости).

Логика `toggleWF`/`toggleOfficeLocation` уже поддерживает и мультивыбор,
и снятие повторным кликом — это чинится само после замены на кнопку,
дополнительная логика не нужна.

### 14.3 Role — чипы вместо одной строки

`profile.role` меняется со строки на массив — уже обновлено в
`profile.json` (`["Product Designer", "UX/UI Designer"]`). Затронутые
места:

**App.jsx** — `defaultProfile.role: ''` → `defaultProfile.role: []`.
В `handleChatSend` сейчас `patch.role = 'Product Designer'`
(перезаписывает полностью) — замени на добавление в массив, не
перезапись:
```js
if (/product designer|продукт.*дизайн/.test(lower)) {
  if (!profile.role.includes('Product Designer')) {
    patch.role = [...profile.role, 'Product Designer']
  }
}
```

**Profile.jsx** — `completenessInfo`: `!!profile.role` →
`profile.role.length > 0`. Сама секция Role:

```jsx
const [roleInput, setRoleInput] = useState('')
const roleSuggestions = ['Product Designer', 'UX/UI Designer', 'Product + UX/UI']

const addRole = (role) => {
  const trimmed = role.trim()
  if (!trimmed || profile.role.includes(trimmed)) return
  onUpdate({ role: [...profile.role, trimmed] })
  setRoleInput('')
}
const removeRole = (role) =>
  onUpdate({ role: profile.role.filter((r) => r !== role) })
```

```jsx
<div className="section">
  <div className="section-head">Role</div>
  <div className="role-chips-input">
    {profile.role.map((r) => (
      <span key={r} className="role-chip">
        {r}
        <button type="button" onClick={() => removeRole(r)} aria-label={`Remove ${r}`}>
          <X size={12} />
        </button>
      </span>
    ))}
    <input
      className="role-chip-input"
      type="text"
      placeholder={profile.role.length ? 'Add another…' : 'e.g. Product Designer'}
      value={roleInput}
      onChange={(e) => setRoleInput(e.target.value)}
      onKeyDown={(e) => { if (e.key === 'Enter') { e.preventDefault(); addRole(roleInput) } }}
    />
  </div>
  <div className="role-suggestions">
    {roleSuggestions.filter((r) => !profile.role.includes(r)).map((r) => (
      <button key={r} type="button" className="role-pill" onClick={() => addRole(r)}>
        + {r}
      </button>
    ))}
  </div>
</div>
```

### 14.4 Sidebar — скруглённые пункты навигации

`.nav-item` сейчас `border-radius: var(--radius-sm)` (8px) + акцент
активного состояния через `border-left: 2px solid`. При общей
пилюльной стилистике приложения это выделяется как "квадратное" рядом
с остальным. Приведи к пилюле, полностью убрав левую полоску (жёсткая
прямая линия плохо сочетается с округлыми краями — активное состояние
и так хорошо читается через заливку):

```css
.nav-item {
  border-radius: var(--radius-full);
  border-left: none;
  padding: 10px 16px;
}
.nav-item.active {
  background: var(--accent-soft);
  color: var(--text-primary);
}
```

### 14.5 Общее правило на будущее — не всё обязано быть пилюлей

Чтобы не перекруглить в другую сторону: **интерактивные, самодостаточные
элементы** (кнопки, чипы, теги, пункты навигации, инпуты) —
`var(--radius-full)`. **Многострочные контентные блоки** (карточка
вакансии, `.settings-card`, drawer, `.ai-note-item`) — оставляем
`var(--radius-lg)`/`var(--radius-md)`, им не нужна форма таблетки, это
контейнеры с содержимым, а не элементы управления. Также проверь hover-
состояния списковых айтемов (`.source-item` в Settings — сейчас
`var(--radius-sm)`, при пилюльных полях ввода вокруг него это тоже
может ощущаться как "квадратное" — можно поднять до `var(--radius-md)`
для более мягкого перехода, не обязательно до полной пилюли).
